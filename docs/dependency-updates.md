# 依存更新の運用

依存パッケージの更新を、**放っておいても安全に取り込まれ、人が見るべきものだけが残る** 形で回すための仕組みと手順。
セキュリティ上の位置付けは [security.md](security.md)、ワークフローの一覧は [infrastructure.md](infrastructure.md) を参照。

## ひとことで

- 毎週、Dependabot が更新の PR を作る。minor / patch はエコシステムごとに 1 つの PR にまとまる。
- CI（`test`）が通れば、**major 以外は自動でマージされる**。
- 人が見るのは、**開いたまま残っている Dependabot の PR だけ**。残っているものには理由がある（下の「人の手が要るもの」）。

## 使うもの

すべて GitHub の無料機能で、外部のサービスや GitHub App は使わない。

| もの | 役割 | 設定 |
| --- | --- | --- |
| Dependabot バージョンアップデート | 毎週、新しい版への更新 PR を作る | `.github/dependabot.yml` |
| Dependabot セキュリティアップデート | 脆弱性が公表された依存の更新 PR を、週次を待たずにすぐ作る | リポジトリ設定（有効） |
| CI（`ci.yml` の `test`） | 更新後もテスト・静的解析・`composer audit` が通るかを確かめる。main へのマージに必須 | ルールセット `protect-main` |
| 自動マージ（`dependabot-automerge.yml`） | Dependabot の PR のうち major を含まないものに、GitHub の自動マージを予約する | ワークフロー + リポジトリ設定 `allow_auto_merge` |

## 流れ

~~~text
毎週 Dependabot                       セキュリティ勧告が出たとき
  │ 公開から 7 日たった版だけ（cooldown） │ 待たずに、依存ごとに個別の PR
  ▼                                     ▼
PR を作る ─────────────────────────────────┘
  ├─ minor / patch … エコシステムごとに 1 つの PR（例: composer の更新をまとめて 1 件）
  └─ major         … 依存ごとに 1 つの PR
  │
  ▼
dependabot-automerge.yml がコミットメッセージの update-type を読む
  ├─ 全部 minor / patch      → 自動マージを予約（gh pr merge --auto --squash）
  └─ major を含む / 判定不可 → 何もしない（PR は開いたまま残る ＝ 人が見る）
  │
  ▼
CI の test
  ├─ 成功 → GitHub がスカッシュでマージ（ブランチは自動で消える）
  └─ 失敗 → マージされず、PR は開いたまま残る ＝ 人が見る
  │
  ▼
main に入った更新は、次の定期実行（毎日 03:17 UTC）のデプロイから使われる
~~~

### 対象のエコシステム

| エコシステム | 場所 | CI で確かめられること |
| --- | --- | --- |
| Composer | `/`（`composer.lock`） | テスト・静的解析・コード整形・`composer audit` |
| GitHub Actions | `.github/workflows/` | `ci.yml` が使う Action は CI で動く。`deploy.yml` だけが使う Action はデプロイまで動かない |
| npm | `/`（`package-lock.json`） | 確かめていない（サイトの生成では使っていない） |
| npm | `/deploy`（wrangler） | 確かめていない。次のデプロイで初めて動く |
| Docker | `/docker`（開発環境のイメージ） | 確かめていない。次に開発環境を作り直したときに動く |

CI で確かめていないものも自動マージする。壊れても次のとおりで、配信中のサイトは壊れない。

- wrangler や `deploy.yml` の Action が壊れた場合: デプロイが失敗し、前回のサイトが残る（Actions の失敗通知で気付く）
- Docker が壊れた場合: 開発環境が起動しない。本番には関係しない

## 人の手が要るもの

**開いたまま残っている Dependabot の PR** だけを見る。週に 1 回、次のコマンドか PR 一覧で確認する。

~~~sh
gh pr list --author app/dependabot
~~~

| 残っている理由 | 見分け方 | やること |
| --- | --- | --- |
| major の更新 | PR タイトルの版の先頭の数字が上がっている。自動マージが予約されていない | リリースノートを読み、必要ならコードを直して（PR のブランチに push するか、別の PR で）マージする |
| update-type を判定できない | 自動マージが予約されておらず、`automerge` ジョブに notice が出ている。推移的な依存のセキュリティ更新などで起きる | 差分（ロックファイルの版）を見て、問題なければ手でマージする。セキュリティ更新なら下の「セキュリティ更新で公開直後の版が入るとき」も確かめる |
| CI が失敗した | PR のチェックが赤い | 失敗の原因を直す。直せない・今は上げられない場合は PR を閉じる（Dependabot は次の版が出るまで同じ PR を作らない） |
| 競合して止まっている | PR が競合（conflicting）になっている。競合している間は CI も自動マージのワークフローも動かない | Dependabot が自分でリベースする。止まっていたら PR に `@dependabot rebase` とコメントする |

自動マージされたあとにも、人が対応するものがある。

| 起きたこと | 気付き方 | やること |
| --- | --- | --- |
| デプロイが失敗した（wrangler など） | Deploy ワークフローの失敗通知 | 直前にマージされた依存更新を revert する PR を作る |
| 開発環境が起動しない（Docker） | `node scripts/devenv.mjs up` の失敗 | イメージの版を戻す PR を作る |

### セキュリティ更新で公開直後の版が入るとき

セキュリティアップデートには cooldown が効かない。脆弱性を直すために、**公開から 7 日たっていない版** が入ることがある
（脆弱な依存を固定している親パッケージごと、最新版に上がる場合など）。マージする前に次を確かめる。

1. 差分で上がる版の公開日を確かめる（`npm view <パッケージ> time --json`、Packagist のリリース日など）
2. 公開から 7 日未満の版が、**シークレットのある場所で動くか** を確かめる。今は wrangler（`deploy/`）だけが、
   `deploy` ジョブで `CLOUDFLARE_API_TOKEN` と一緒に動く
3. 該当する場合は、マージするか待つかを、脆弱性の深刻さ・このプロジェクトで実際に突かれうるか・その版の信頼性で決める。
   信頼性は次で確かめる
   - npm の provenance（公開元が本家リポジトリのワークフローか）、`deprecated` になっていないか
   - 本家の Issue・リリースノート、SNS などで、その版に問題の報告がないか
4. 待つ場合は、公開から 7 日たってから、`test` が通っていることを確かめてマージする

### 人が PR に手を入れたとき

人が Dependabot のブランチに push すると、自動マージは予約されない（`automerge` ジョブはきっかけが Dependabot のときだけ動く）。
手を入れた PR は、人が確認してマージする。

## 安全のための決めごと

- **cooldown 7 日**: 公開から 7 日たった版だけを取り込む。乗っ取られたアカウントから公開された悪意ある版は、
  多くの場合、数日のうちに見つかって取り下げられる。それを自動マージで main に入れないための待ち時間。
  セキュリティアップデートには効かないので、脆弱性の修正は待たずに入る。
- **major は自動マージしない**: 互換性のない変更を含みうるため。
- **自動マージは「予約」だけ**: マージするのは GitHub で、必須チェック `test` が通ったときだけ。
  ワークフローは PR を **承認しない**（Actions による承認は禁止のまま。ルールセットは承認 0 件で通る）。
- **ワークフローは PR のコードを実行しない**: チェックアウトせず、GitHub API でコミットメッセージを読むだけ。
  書き込み権限（`contents: write` / `pull-requests: write`）は `automerge` ジョブだけに付ける。
- **きっかけが Dependabot のときだけ動く**: PR の作成者と、実行のきっかけ（作成・push）を起こしたユーザーの両方が `dependabot[bot]` であることを確かめる。

### 自動マージの副作用

`GITHUB_TOKEN` によるマージは、ほかのワークフローを起動しない（GitHub の仕様）。そのため、自動マージ後の main への push では `ci.yml` が動かない。
PR の時点で `test` が通っているので、これは許容する。

## 設定を変えるとき

- 自動マージの範囲（今は major 以外すべて）を変える: `dependabot-automerge.yml` の判定と、この文書を変える
- まとめ方・待ち日数を変える: `.github/dependabot.yml` の `groups` / `cooldown` と、この文書を変える
- 自動マージをやめる: リポジトリ設定 `allow_auto_merge` を無効にすれば、ワークフローの予約が失敗して PR が残る（その後ワークフローを消す）
