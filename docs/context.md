# プロジェクトの経緯と決めたこと

別のセッション・別の PC・別のエージェントがこのプロジェクトを引き継ぐための文書。
「なぜこうなっているか」を残す。実装の詳細は [architecture.md](architecture.md) を参照。

最終更新: 2026-10-12

## 1. 始まり

- オーナーは Laravel / PHP を読み書きでき、2026-10 に [Larastan](https://github.com/larastan/larastan) へ初めての OSS 貢献をした。
  - [larastan/larastan#2573](https://github.com/larastan/larastan/pull/2573)（`incrementEach()` / `decrementEach()` のカラム名チェック）: マージ済み
  - [larastan/larastan#2581](https://github.com/larastan/larastan/pull/2581)（`incrementOrCreate()` のカラム名チェック）: レビュー待ち
- Larastan のコントリビューターとして、自分のプロジェクトでも Larastan を実戦で使いたい、というのが出発点。

## 2. 制約・好み

- **他人の個人情報を預からない。** ログイン機能やユーザー登録を作らない。
- **Laravel を使い倒す。** Larastan が一番効くのは Eloquent を多用するコードなので、DB をしっかり使う題材にする。
- **お金をかけない。** VPS も借りない無料構成で始める（理由は 5 章）。
- **ポートフォリオとして見栄えがすること。** ただし、自分の実績の量に見栄えが左右される題材（例: 自分の OSS 貢献トラッカー）は、実績が少ない今は避けた。

## 3. 題材を選んだ理由

Larastan の貢献作業で、「このメソッドは Laravel のどのバージョンから存在するか」を調べる必要があった
（スタブは「そのメソッドが有効な最も古いバージョン」に置く規則があるため）。
このとき GitHub API でタグを 1 つずつ取得してソースを grep するしかなかった。この作業をサービスにする。

- データは Laravel のソースコードだけなので、個人情報がゼロ。
- データ量は Laravel のリリースごとに自動で増える（放っておいても育つ）。
- モデル（リリース・クラス・メソッド・引数・変更履歴）が多く、Eloquent・キュー・スケジューラを自然に使う。
- 「Larastan のスタブに型が足りないメソッド」を出せれば、オーナー自身の次の貢献先探しにも使える。

## 4. 既存のものとの違い（2026-10 時点の調査）

メソッドごとに「いつ追加・変更されたか」を逆引きできるサービスは見つからなかった。近いもの:

| 既存のもの | できること | できないこと |
| --- | --- | --- |
| Laravel 公式ブログのリリース記事・Laravel News | 各リリースで追加されたメソッドを文章で紹介 | メソッド名から逆引きできない。引数の型の変更までは追えない |
| GitHub の compare 画面 | 2 バージョン間の生の差分 | 人が読み解く必要がある |
| [verdiff](https://nickjanetakis.com/blog/a-python-cli-tool-to-help-diff-web-framework-versions) | 2 バージョンの新規プロジェクトの差分 | 雛形ファイルの差分で、フレームワーク API の差分ではない |

差別化ポイント: **メソッド名からの逆引き**、**シグネチャ（型・既定値）の変更の追跡**、**Larastan のスタブとの突き合わせ**。

## 5. 構成を無料にした理由

- Cloudflare Workers は PHP を実行できない。Cloudflare Containers なら Laravel は動くが、無料プランでは使えない（公式ドキュメント上は有料プラン月 5 ドルから。料金ページとは記載が食い違っていた）。
- Laravel Cloud は「月 0 ドル + 使用量」のプランがあるが、完全な無料ではない。
- このサイトは **データが変わるのが Laravel のリリース時だけ** なので、常時動くサーバーは要らない。
  → GitHub Actions の定期実行で Laravel をバッチとして動かし、静的サイトを Cloudflare Pages に置く。
- VPS は「運用の手間と攻撃面が増える」ため今は借りない。次のどれかに当てはまったら移行を検討する:
  1. 検索・Livewire 画面・API など、リクエストを受けてその場で返す機能が必要になった
  2. ほかの個人プロジェクトもまとめて置きたくなった
  3. サーバー運用そのものをポートフォリオにしたくなった
- コードはスケジューラ・キュー・Artisan コマンドという普通の Laravel の作りで書く。VPS に移すときは置き場所を変えるだけで済むようにする。

## 6. 公開範囲とセキュリティ

- リポジトリは **public**（ポートフォリオとして見せるため。GitHub Free でもブランチの保護ルールやシークレットスキャンのプッシュ保護が使える）。
- 開発者はオーナー 1 人。**オーナー以外が、リポジトリ・CI・配信先に変更を加えられないこと** を最優先にする。
  詳細は [security.md](security.md)。

## 7. 決めたこと一覧

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| リポジトリ名 | `laravel-since` | 「いつから？」を引くサービスであることを名前で表す |
| Laravel / PHP | Laravel 13 / PHP 8.5 | 作成時点の最新 |
| DB | SQLite | バッチで作って捨てられる。サーバー不要 |
| ソース解析 | `nikic/php-parser` で構文として読む | 取得した Laravel のコードを **実行しない** ため（安全性） |
| アーキテクチャ | Onion Architecture | Domain を Laravel・外部 I/O から独立させ、技術詳細を外側の Infrastructure に置く |
| 対象範囲 | まず `laravel/framework` の 11.0.0 以降 | Larastan の対応範囲に合わせる。範囲は設定で広げられるようにする |
| 配信 | Cloudflare Pages（Direct Upload） | 無料。Git 連携ではなく Actions からアップロードし、PR からのビルドを走らせない |
| ライセンス | MIT | Laravel 本体・エコシステムに合わせた |
| ドキュメントの言語 | 日本語（README の冒頭のみ英語） | オーナーの作業言語。公開後に英語化を検討 |
